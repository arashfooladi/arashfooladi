ابزار توسعه

ابزارهای کدنویسی در ترمینال که استفاده می‌کنم

نوشته آرش فولادی ۲۳ مرداد ۱۴۰۵ حدود ۸ دقیقه مطالعه

بخش زیادی از کار روزانه من داخل ترمینال می‌گذرد. نه به این دلیل که رابط گرافیکی بد است؛ ترمینال برای من سریع‌تر، قابل تکرارتر و نزدیک‌تر به خود پروژه است. در ماه‌های اخیر سه ابزار بیشتر از بقیه در این جریان حضور داشته‌اند: Reasonix، Codex و OpenCode.

این سه ابزار یک کار واحد را به سه شکل متفاوت انجام می‌دهند. هر سه می‌توانند کد را بخوانند، فایل تغییر دهند و دستور اجرا کنند، اما تفاوت واقعی در مدیریت context، مدل‌های قابل استفاده، هزینه و میزان کنترلی است که روی روند کار می‌دهند. برای همین به‌جای انتخاب یک «برنده»، هرکدام را برای نوع مشخصی از کار نگه داشته‌ام.

Reasonix؛ وقتی جلسه طولانی و هزینه مهم است

Reasonix یک عامل کدنویسی terminal-first است که طراحی آن حول مدل‌های DeepSeek و prefix cache شکل گرفته. ایده اصلی ساده است: بخش ثابت context باید تا حد ممکن بدون تغییر باقی بماند تا در هر درخواست دوباره با قیمت کامل پردازش نشود.

Reasonix تاریخچه را به‌شکل append-only نگه می‌دارد و تلاش می‌کند prefix قبلی دقیقاً قابل استفاده بماند. نتیجه در جلسه‌های طولانی محسوس است؛ هرچه گفتگو و نقشه پروژه بزرگ‌تر می‌شود، بخش بیشتری از ورودی از cache برمی‌گردد. برای refactorهای طولانی، بررسی یک codebase بزرگ یا کاری که چند ساعت ادامه دارد، این رفتار تفاوت زیادی ایجاد می‌کند.

در یکی از بازه‌های کاری من، آمار مصرف به حدود ۸۰۰ میلیون توکن رسید و هزینه کل تقریباً ۴ دلار شد. مدلی که استفاده می‌کردم dsv4flash0731 بود.

این عدد یک benchmark عمومی نیست. قسمت بزرگی از آن ۸۰۰ میلیون توکن، prefixهای تکراری و cache‌شده بود؛ یعنی تعداد خام توکن با مقدار محاسبه تازه برابر نیست. نرخ API، مدل و درصد cache-hit مستقیماً روی هزینه اثر می‌گذارند. بااین‌حال برای من نشان داد که یک loop درست طراحی‌شده چقدر می‌تواند هزینه جلسه‌های طولانی را پایین بیاورد.

Reasonix را بیشتر زمانی باز می‌کنم که قرار است مدت زیادی در یک مخزن بمانم، context مرتب رشد کند و نخواهم برای هر دور دوباره هزینه کامل همان اطلاعات ثابت را بدهم.

Codex؛ برای کار جدی روی کل مخزن

Codex را برای کارهایی ترجیح می‌دهم که فقط تولید یک snippet نیستند: پیدا کردن مسیر یک قابلیت در codebase، ایجاد تغییر در چند فایل، اجرای تست‌ها، بررسی diff و رساندن کار به نقطه‌ای که واقعاً قابل تحویل باشد.

مزیت اصلی برای من این است که می‌توانم هدف را در سطح feature یا bug توضیح بدهم و روند کار همچنان حول خود مخزن بماند. Codex فایل‌ها را بررسی می‌کند، تغییرات را اعمال می‌کند و نتیجه را با تست یا بررسی‌های مرتبط می‌سنجد. برای taskهایی که نیاز به دقت، پیگیری چندمرحله‌ای و کنترل تغییرات دارند، این مدل کار از یک چت ساده مفیدتر است.

البته همچنان diff نهایی را خودم می‌خوانم. هرچه ابزار مستقل‌تر عمل کند، اهمیت review بیشتر می‌شود؛ مخصوصاً برای authentication، پرداخت و هر چیزی که با داده کاربر درگیر است.

OpenCode؛ انعطاف در انتخاب مدل و provider

OpenCode یک عامل کدنویسی متن‌باز است که در ترمینال، IDE و دسکتاپ قابل استفاده است. چیزی که آن را برای من جذاب می‌کند انعطاف آن در اتصال به providerها و مدل‌های مختلف است. لازم نیست کل گردش کار را با عوض شدن مدل کنار بگذارم.

OpenCode برای مقایسه مدل‌ها، راه‌اندازی سریع یک TUI تمیز و پروژه‌هایی که می‌خواهم provider را خودم انتخاب کنم مناسب است. امکان داشتن sessionهای مختلف و agentهای جدا برای build، plan یا review نیز باعث می‌شود یک ابزار عمومی‌تر باشد.

در عمل اگر بخواهم یک مدل تازه را روی همان پروژه امتحان کنم، OpenCode معمولاً سریع‌ترین مسیر من است. اگر هزینه و cache در یک جلسه بسیار طولانی اولویت اصلی باشد سراغ Reasonix می‌روم، و برای اجرای دقیق یک کار سرتاسری روی مخزن بیشتر به Codex تکیه می‌کنم.

مقایسه کوتاه

ابزار نقطه قوت اصلی جایی که بیشتر استفاده می‌کنم
Reasonix prefix cache و جلسه‌های طولانی کم‌هزینه بررسی طولانی codebase و refactorهای پیوسته
Codex کار چندمرحله‌ای روی مخزن، تست و review feature، رفع باگ و آماده‌سازی تغییر قابل تحویل
OpenCode متن‌باز بودن و آزادی انتخاب provider آزمایش مدل‌ها و گردش کار قابل تنظیم

ابزارهای کوچک‌تری که این جریان را کامل می‌کنند

عامل کدنویسی به‌تنهایی کافی نیست. چند ابزار ساده تقریباً در تمام جلسه‌ها کنار آن‌ها هستند:

  • git برای اینکه هر تغییر قابل مشاهده و قابل برگشت باشد.
  • rg یا ripgrep برای جست‌وجوی سریع متن و مسیرها در مخزن.
  • gh برای بررسی issue، pull request و وضعیت repository بدون خروج از ترمینال.
  • curl برای تست مستقیم endpointها و دیدن پاسخ واقعی API.
  • jq برای خواندن و فیلتر کردن JSON در pipelineهای کوچک.

ترکیب این ابزارها مهم‌تر از تعدادشان است. مثلاً یک agent می‌تواند مسیر مرتبط را با rg پیدا کند، تغییر را بسازد، تست را اجرا کند و در پایان با git diff دقیقاً نشان دهد چه اتفاقی افتاده است. این جریان هم سریع است و هم قابل بررسی.

روشی که برای من بهتر جواب داده

  1. هدف را محدود می‌کنم. یک feature یا یک باگ مشخص، نه «کل پروژه را بهتر کن».
  2. اول وضعیت موجود را می‌خوانم. ساختار مخزن و تست‌های فعلی قبل از هر edit مشخص می‌شوند.
  3. ابزار را بر اساس task انتخاب می‌کنم. هزینه، طول جلسه و آزادی مدل سه معیار اصلی‌اند.
  4. تست و diff داور نهایی‌اند. پاسخ خوب در ترمینال جای کد درست و تست‌شده را نمی‌گیرد.
  5. context را بی‌دلیل شلوغ نمی‌کنم. فایل و توضیح مرتبط بهتر از ریختن کل پروژه در یک prompt است.

جمع‌بندی

برای من CLI فقط شکل دیگری از یک ویرایشگر نیست؛ جایی است که کد، تست، version control و agent در یک جریان واحد کنار هم قرار می‌گیرند. Reasonix هزینه جلسه‌های طولانی را قابل کنترل کرده، Codex برای کار سرتاسری روی مخزن قابل اتکاست و OpenCode آزادی انتخاب مدل را حفظ می‌کند.

بهترین ابزار همان ابزاری است که خروجی‌اش را بتوانم بفهمم، تست کنم و مسئولیتش را بپذیرم. سرعت مهم است، اما کنترل روی تغییرات مهم‌تر است.
