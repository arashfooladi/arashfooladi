کاربر «جاوا» را جست‌وجو می‌کند، بعد سریع می‌نویسد «جاوااسکریپت». نتیجهٔ عبارت دوم می‌آید و درست نمایش داده می‌شود. چند لحظه بعد، پاسخ درخواست اول از راه می‌رسد و همان نتیجهٔ درست را پاک می‌کند. کد خطا نداده؛ صفحه فقط دارد جواب سؤال قبلی را نشان می‌دهد.

دو درخواست، یک کادر نتیجه

اگر با هر تغییر ورودی یک fetch بفرستیم، ترتیب شروع درخواست‌ها را می‌دانیم. ترتیب تمام شدنشان تضمین‌شده نیست. پاسخ اول ممکن است به خاطر شبکه، کش یا زمان پردازش سرور دیرتر برسد.

Input:    "java"       "javascript"
Request:  A starts     B starts
Response:             B finishes     A finishes
Screen:               javascript     java

این یک نمونه از Race Condition است: نتیجهٔ نهایی به ترتیب رخدادها وابسته شده است. برای بروز چنین باگی نیازی به چند نخ جاوااسکریپت نداریم؛ جابه‌جا شدن زمان تکمیل کارهای ناهمگام کافی است. حتی اگر هر دو پاسخ کاملاً معتبر باشند، یکی از آن‌ها دیگر به ورودی فعلی مربوط نیست.

چرا debounce کافی نیست؟

با debounce کمی صبر می‌کنیم تا تایپ کاربر متوقف شود و بعد درخواست می‌فرستیم. این کار تعداد درخواست‌ها را کم می‌کند. اما فرض کن کاربر به اندازهٔ کافی مکث کرده، درخواست اول رفته و دوباره شروع به تایپ کرده است. حالا باز هم دو درخواست می‌توانند هم‌زمان در جریان باشند.

تأخیر ۳۰۰ میلی‌ثانیه‌ای تضمینی برای ترتیب پاسخ‌ها نمی‌دهد. برای درستی نمایش نتیجه باید مشخص کنیم کدام درخواست هنوز اجازه دارد صفحه را تغییر بدهد.

هر پاسخ اجازهٔ تغییر صفحه را ندارد

دو کار مکمل داریم: با AbortController دریافت قبلی را لغو کنیم و برای هر جست‌وجو یک شماره بگذاریم. پیش از نمایش نتیجه، شمارهٔ آن را با آخرین شماره مقایسه کنیم. اگر قدیمی بود، پاسخ را کنار بگذاریم.

لغو کردن fetch و خواندن بدنهٔ پاسخ را متوقف می‌کند، اما نباید فرض کنیم هر کاری که بعد از آن شروع شده هم خودکار لغو می‌شود. ممکن است پردازش دیگری یا یک لایهٔ کش، سیگنال لغو را پشتیبانی نکند. شمارهٔ درخواست، شرط تغییر رابط کاربری را روشن نگه می‌دارد. لغو درخواست در مرورگر هم تضمین نمی‌کند پردازش سمت سرور متوقف شده باشد.

یک پیاده‌سازی کوچک

این مثال برای یک جست‌وجوی خواندنی است. فرض می‌کنیم مسیر /api/search آرایه‌ای از رکوردهای دارای title برمی‌گرداند. HTML زیر را در یک صفحه بگذار و جاوااسکریپت را پس از آن، یا در یک اسکریپت defer، اجرا کن. این مقاله خودش آن API را اجرا نمی‌کند.

<label for="search">جست‌وجوی مقاله</label>
<input id="search" type="search" aria-controls="results">
<p id="search-status" role="status"></p>
<ul id="results"></ul>
const input = document.querySelector("#search");
const results = document.querySelector("#results");
const status = document.querySelector("#search-status");
let revision = 0;
let controller;

async function search(query) {
  const mine = ++revision;
  controller?.abort();
  controller = null;
  results.replaceChildren();

  if (!query) {
    status.textContent = "";
    return;
  }

  controller = new AbortController();
  const { signal } = controller;
  status.textContent = "در حال جست‌وجو…";

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal }
    );
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const items = await response.json();
    if (mine !== revision) return;

    results.replaceChildren(...items.map(item => {
      const li = document.createElement("li");
      li.textContent = item.title;
      return li;
    }));
    status.textContent = items.length
      ? `${items.length} نتیجه`
      : "نتیجه‌ای پیدا نشد.";
  } catch (error) {
    if (mine !== revision || error.name === "AbortError") return;
    status.textContent = "جست‌وجو انجام نشد. دوباره امتحان کن.";
  }
}

input.addEventListener("input", () => search(input.value.trim()));

شمارهٔ revision قبل از بررسی خالی بودن عبارت تغییر می‌کند. پس اگر کاربر ورودی را پاک کند، پاسخ در راه هم اعتبارش را از دست می‌دهد و نمی‌تواند دوباره نتایج را روی صفحه بیاورد.

شاخهٔ خطا هم شماره را بررسی می‌کند؛ خطای یک درخواست قدیمی نباید پیام وضعیت جست‌وجوی جدید را عوض کند. همچنین fetch برای پاسخ‌هایی مثل 404 و 500 به‌تنهایی خطا پرتاب نمی‌کند، برای همین response.ok را جداگانه می‌سنجیم.

عنوان نتیجه با textContent وارد صفحه می‌شود تا متن API به‌عنوان HTML اجرا نشود. در این نمونه نتیجهٔ قبلی هنگام تایپ پاک می‌شود؛ این یک انتخاب برای رابط کاربری است. می‌توان آن را نگه داشت، به شرط اینکه روشن باشد نتیجه هنوز در حال به‌روزرسانی است.

باگ را عمداً بازسازی کن

تست کردن فقط با اینترنت سریع ممکن است این مشکل را پنهان کند. در یک پاسخ‌دهندهٔ آزمایشی، تکمیل درخواست‌ها را خودت کنترل کن. ترتیب زیر باید همیشه نتیجهٔ یکسانی بدهد:

  1. جست‌وجوی «جاوا» را شروع کن و پاسخ آن را نگه دار.
  2. جست‌وجوی «جاوااسکریپت» را شروع کن و پاسخ آن را زودتر برگردان.
  3. حالا پاسخ قدیمی را برگردان. صفحه باید همچنان نتایج «جاوااسکریپت» را نشان بدهد.
  4. همین سناریو را با خطای درخواست قدیمی تکرار کن؛ پیام موفقیت جست‌وجوی جدید باید باقی بماند.
  5. در میانهٔ درخواست، ورودی را خالی کن. رسیدن پاسخ دیررس نباید نتایج را دوباره ظاهر کند.

برای آزمودن خودِ محافظ شماره، پاسخ‌دهندهٔ تست را طوری بساز که سیگنال لغو را نادیده بگیرد. با این کار مطمئن می‌شوی درست بودن صفحه فقط به لغو موفق درخواست وابسته نیست. اگر بعداً debounce اضافه کردی، اعتبار درخواست قبلی را همان لحظهٔ تغییر ورودی باطل کن؛ منتظر پایان تایمر نمان.

فراتر از کادر جست‌وجو

همین اتفاق در فیلتر محصولات، عوض کردن تب‌ها یا باز کردن سریع چند پروفایل هم رخ می‌دهد. پیش از نوشتن شرط‌ها، یک قاعدهٔ ساده برای صفحه تعریف کن: داده‌ای که نمایش می‌دهم باید به آخرین انتخاب کاربر مربوط باشد. بعد مسیر موفقیت، خطا و پاک شدن ورودی را با همان قاعده بررسی کن.

این الگو برای تازه ماندن دادهٔ نمایشی است. در عملیاتی مثل پرداخت یا ثبت سفارش، لغو درخواست و نادیده گرفتن پاسخ برای جلوگیری از اجرای تکراری کافی نیست؛ آنجا کنترل تکرار و وضعیت عملیات باید در سرور هم انجام شود. در یادداشت طراحی پرداخت برای یارپلاس به همین ملاحظات پرداخته شده است.
